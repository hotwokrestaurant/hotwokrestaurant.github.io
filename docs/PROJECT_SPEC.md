# Hot Wok Restaurant — QR Digital Menu: Project Specification

Version 2.0 (Firebase backend) · Place this file at `docs/PROJECT_SPEC.md`.

---

## 1. Goals

| # | Goal |
|---|---|
| G1 | Customers scan a QR code and see a clear, fast, mobile-friendly menu. |
| G2 | The owner can change prices, mark items sold out, add and delete items **from their phone only**. |
| G3 | Zero running cost, no payment features, no paid tools. |
| G4 | Simple enough for a beginner developer to understand and maintain. |

### Out of scope (v1)
Online ordering, payments, table numbers, customer accounts, reviews, delivery, dish photo upload from the admin page (not planned: Cloud Storage needs billing; photos are added to `images/` by the developer), multiple languages (planned for v2).

---

## 2. Architecture

```
Customer phone ──scan QR──► index.html  (GitHub Pages)
                                │ 1 read: REST GET menu/published   [plain fetch(), no SDK]
                                ▼
                    Cloud Firestore  (Spark free plan, asia-south1)
                       ▲    protected by firebase/firestore.rules
                       │ sign in (Firebase Auth) + save menu/published   [Firestore + Auth SDK]
Owner phone ──home icon──► admin.html  (GitHub Pages)
```

- Firestore = database. Firebase Authentication = owner login. Security rules = all access control and validation. GitHub Pages = static hosting. **No server code.**
- Customer menu: **https://hotwokrestaurant.github.io/** · Admin: **https://hotwokrestaurant.github.io/admin.html**
- Repo: `hotwokrestaurant/hotwokrestaurant.github.io` (GitHub organization Pages site; the repo name must stay exactly this for the root URL to work).
- The customer page only reads (one document per visit). The admin page reads and writes.
- **Spark plan only.** Nothing that needs billing: no Blaze upgrade, no Cloud Storage, no Cloud Functions, no paid extensions.
- Setup instructions: `firebase/README.md`.

## 3. Data model (Cloud Firestore)

### 3.1 The menu document: `menu/published`

The **whole published menu is one document**, so each customer visit costs a single read. Its shape is the same as `firebase/menu-seed.json`, plus `updatedAt`, so the rendering code works unchanged.

| Field | Type | Notes |
|---|---|---|
| `settings` | map | See 3.4 |
| `categories` | array of maps | See 3.3. 1–8 entries |
| `items` | array of maps | See 3.2. Up to 200 entries |
| `updatedAt` | timestamp | Set with `serverTimestamp()` on every save (the rules require the server's clock) |

The document is about 5 KB with 18 dishes. Firestore's limit is 1 MiB, so size is never a concern.

### 3.2 Items (dishes): entries of `items`

| Field | Type | Rules / example |
|---|---|---|
| `id` | string | `itm_` + 4–20 lower-case letters/digits, e.g. `itm_ko0001`. Generated by the admin page, never typed by hand. |
| `category` | string | Must be one of the known categories (3.3). e.g. `Kottu` |
| `name` | string | Required, 1–60 chars. e.g. `Chicken Kottu` |
| `description` | string | Optional, ≤ 150 chars (`''` = none) |
| `price` | integer | Required, whole rupees, 1–100,000. e.g. `1200` |
| `price_large` | integer or `null` | Optional. `null` = one size only |
| `spicy` | boolean | |
| `veg` | boolean | |
| `available` | boolean | `false` = sold out today (hidden, or faded if `show_sold_out`) |
| `featured` | boolean | Shows the "Chef's special" icon |
| `image` | string | Optional. Simple file name in the repo's `images/` folder, e.g. `chicken-kottu.webp`; `''` = no photo. **Set by the developer only; the admin page never handles images.** |
| `sort_order` | integer | 0–10,000. Lower shows first within its category |

### 3.3 Categories: entries of `categories`

| Field | Type | Example |
|---|---|---|
| `name` | string | Must be in the known list: Fried Rice, Kottu, Noodles, Devilled Dishes, Soups, Side Dishes, Beverages, Desserts |
| `sort_order` | integer | `1` |
| `visible` | boolean | `true` |

Adding a new category means adding it to `categoryNamePattern()` in `firebase/firestore.rules` (and republishing the rules) as well as to the data.

One document per owner account; the document ID is the account's Firebase Auth **UID**. Example field: `name: "Owner"`. Created and removed by hand in the Firebase console. The apps can neither read nor write this collection.

## 4. Firebase access

### 4.1 How each page talks to Firebase (no build step)
- **Customer page: no Firebase SDK.** It reads the public document with one plain `fetch()` to the Firestore REST API:
  `GET https://firestore.googleapis.com/v1/projects/<projectId>/databases/(default)/documents/menu/published?key=<apiKey>`
  - The response is about 1.9 KB compressed, instead of about 61 KB of SDK code.
  - It's a simple GET, so the browser skips its extra CORS check request.
  - Firestore allows the `hotwokrestaurant.github.io` origin.
  - The security rules apply as for any signed-out visitor.
  - A small converter in `js/api.js` turns Firestore's typed values back into plain values: `stringValue`, `integerValue` (sent as text, converted to a number), `doubleValue`, `booleanValue`, `nullValue`, `timestampValue` (converted to milliseconds), `arrayValue`, `mapValue` (keys sorted).
- **Admin page:** Firebase **modular SDK** as ES module imports from Google's official CDN, **pinned to one version** in every URL: `https://www.gstatic.com/firebasejs/12.19.0/<file>.js` (`firebase-app.js` + `firebase-firestore.js` + `firebase-auth.js`). Upgrade by changing every URL together and re-testing.
- Config (`FIREBASE_CONFIG`) and the document path (`MENU_COLLECTION` / `MENU_DOC_ID`) live in `js/config.js`. The web config is not a secret.

### 4.2 Customer reads (Phase 3, `js/api.js` + `js/menu.js`)
1. On load, render the **saved** menu from `localStorage` (key `hotwok.menu.v1`: `{ menu, updatedAt }`, `updatedAt` in milliseconds) immediately, if one exists. Otherwise the skeleton stays.
2. Fetch the latest menu with **one REST `fetch()`** (see 4.1; = 1 read per visit). Nothing has to download first, so it never delays the saved menu or the skeleton. `index.html` preconnects to Firestore and `modulepreload`s the page's own helper modules.
3. A **timeout** covers the whole download and cancels it (`AbortController`): 20 s on a first visit, 10 s when a saved menu is already shown (`js/config.js`).
4. On success: redraw **only if the menu changed** (`updatedAt` differs, or the contents differ, which catches hand edits in the Firebase console that don't touch `updatedAt`), and save to `localStorage` (try/catch). A redraw keeps any search text and skips the fade-in.
5. On failure (offline, timeout, missing/invalid data): with a saved menu, show the small note "Showing saved menu · updated 29 Oct"; with none, show a friendly message with **Try again** and **Call us** (number from `FALLBACK_PHONE` in `js/config.js`). When the phone comes back online, the menu quietly retries.
6. Filtering stays in the browser: only `visible` categories; only `available` items unless `show_sold_out`.
7. **No sample data in the live site.** All text, including the "Sample menu – prices are placeholders" notice, comes from `settings` in Firestore. `js/sample-data.js` was removed in Phase 3; `firebase/menu-seed.json` is the reference data.
8. A fully offline **first** page load can't work without a service worker (not in v1). "Offline" here means the page itself loaded (from the network or the browser's cache) but Firestore couldn't be reached.

Measured (headless Chrome against the live project, 412px wide). The REST fetch replaced Firestore Lite because it was clearly faster on first visits and behaved the same in every failure test:

| Scenario | Firestore Lite SDK | **REST fetch (current)** |
|---|---|---|
| First visit, normal connection | 2.5 s | **1.0–1.2 s** |
| Repeat visit | 0.1 s (saved copy) | **0.1 s** (saved copy) |
| Slow 3G, first visit (3 runs) | 12.0–12.4 s | **7.7–8.2 s** |
| Slow 3G, repeat visit, no browser cache (3 runs) | 5.5–5.6 s | **5.5–5.6 s** (saved copy; page files take the time) |
| Firestore unreachable, saved copy | 0.1 s + note | **0.1 s + note** |
| Firestore unreachable, nothing saved | error at 0.9 s | **error at 0.5–0.8 s** |
| Firestore not answering, saved copy | note at 10 s | **note at 10 s** |
| Firestore not answering, nothing saved | error at 21 s | **error at 21 s** |
| Saved copy out of date (same `updatedAt`) | corrected | **corrected** |

### 4.3 Owner writes (Phase 4): never overwrite the menu
The admin page **never** writes the whole document with `setDoc`. Every change (toggle sold out, edit, add, delete, reorder, settings) is a **transaction that updates only the field it changes**:

```js
await runTransaction(db, async (tx) => {
  const snap = await tx.get(menuRef);                    // 1. read the LATEST menu
  const items = snap.data().items.map((it) =>
    it.id === dishId ? { ...it, available: false } : it); // 2. change one dish in it
  tx.update(menuRef, { items, updatedAt: serverTimestamp() }); // 3. write only items + updatedAt
});
```

- **Why a transaction:** if another phone saves between steps 1 and 3, Firestore notices that the document changed and **re-runs the function with the fresh menu**. Two phones editing different dishes at the same moment both keep their change; neither can wipe the other's.
- **Why `tx.update` of one field:** a dish change writes only `items` (+ `updatedAt`); a settings change writes only `settings`; a category change writes only `categories`. Unrelated parts of the document are never rewritten.
- **Why not `items.<id>` field paths:** that only works if `items` is a map. The data model keeps `items` as an array (same shape as `firebase/menu-seed.json`), and the transaction gives the same protection.
- **Tested** against the current rules in the Firestore emulator: two simultaneous transactions on different dishes keep both edits; a settings-only transaction leaves dishes untouched; an invalid dish inside a transaction is still rejected. No rule changes are needed.
- If the same dish is edited on two phones at once, the later save wins for that dish (expected).
- Each save sets `updatedAt: serverTimestamp()`.
- **A save may add or change at most 3 dishes**, and **a save that changes the categories can't also change dishes** (rules limits, see 4.4). Normal actions touch 1 dish (reorder: 2). Deleting dishes is unlimited. Settings may change together with dishes.
- New dish: `id` = `itm_` + random lower-case letters/digits, `available: true`, `sort_order` = last in its category.
- Frontend validation mirrors the rules (same limits) so the owner gets friendly messages, but the **rules are the real check**.

### 4.4 Security rules (`firebase/firestore.rules`)
- **Read:** anyone can `get` `menu/published`. Listing collections and reading anything else are denied.
- **Write:** only signed-in users whose UID has a document in `admins`, and only if the new document is valid:
  - Exact top-level fields, and `updatedAt == request.time`.
  - Settings types and sizes; category entries from the known list.
  - Every **new or changed** dish fully validated: types, name ≤ 60, description ≤ 150, prices positive integers, category known, safe image name, no unknown fields.
- **Why only changed data:** rules have no loops, so they can't check every dish in a long list. They compute `newItems.removeAll(oldItems)`, require at most 3 entries, and validate each. Settings and categories are likewise only checked when they differ from the saved copy. Every value is therefore validated when it's written.
- **Why the limits are 3 dishes and "categories alone":** Firestore stops evaluating a rule after 1,000 steps. Measured in the emulator (with 18 and 150 dishes), every allowed save fits. Checking all 8 categories and several dishes in one save would not, so that combination is refused by an explicit rule.
- **`admins` is read- and write-locked for every app** (`allow read, write: if false`). Only the Firebase console can change it, so an account created through the Auth API can't add itself. Public sign-up is also turned off in Authentication → Settings → User actions, where the console offers it.
- No deletes of the menu document. Everything not matched is denied.
- Tested in the Firestore emulator (60 checks, all passing, including the `admins` lockdown and simultaneous transactions) before handover; manual tests are in `firebase/README.md`.

### 4.5 Owner authentication
- Email/password. The owner's account is created by hand in the console. **No sign-up flow** in the app (and "Enable create (sign-up)" is turned off in the console where available).
- **Persistence:** `browserLocalPersistence`, so the owner stays signed in on their phone until they press **Log out**.
  - iPhone Safari may clear site storage after ~7 days without a visit. Adding the admin page to the Home Screen (Phase 5) avoids this. Otherwise the owner just signs in again.
- Authorized domains: `hotwokrestaurant.github.io` and `localhost`.

### 4.6 App Check
Not enabled in v1. reCAPTCHA would slow the customer page on 3G and can block real customers, and the rules already stop any unauthorized changes. Reconsider only if usage shows abuse. Full reasoning: `firebase/README.md`.

### 4.7 Backups (no automatic backups on Spark)
- **Phase 4:** a **"Download backup"** button in the admin page saves `menu/published` as a `.json` file in the same shape as `firebase/menu-seed.json` (`settings`, `categories`, `items`; no `updatedAt`). File name like `hot-wok-menu-backup-2026-11-03.json`. Uses the read the admin page has already done; no extra cost.
- **Restore:** `firebase/setup.html` gets a **"Load from a backup file"** option. It reuses the seed loader: categories first, then 3 dishes per save, so the rules check everything.
- **Optional later:** a scheduled GitHub Action reads the public document once a day and commits it to a separate `backups` branch. That's free, needs no credentials, and doesn't trigger a Pages deploy.
- Owner guidance: download a backup after big changes and monthly; keep it in Google Drive or email.

### 4.8 What is published
GitHub Pages publishes the repo root, except what `_config.yml` excludes: `firebase/` (rules, seed, setup page, guide), `docs/`, `tools/`, `CLAUDE.md`, `README.md`. Developer tools therefore stay in the repo but are never served. Don't add a `.nojekyll` file; the exclusions rely on Pages' default Jekyll build. Check after each deploy that `/firebase/setup.html` returns 404.

### 4.9 Free limits (Spark)
50,000 reads, 20,000 writes and 20,000 deletes per day; 1 GiB stored. Each customer visit = 1 read. Hitting a limit pauses Firestore until the daily reset (no charges); customers then see the cached menu.

## 5. Customer menu — `index.html`

### Layout (top to bottom)
1. **Header:** logo image (`images/logo.webp`, the wordmark cropped from the original `images/logo.jpg`, shown 232px wide) as the page title, optional tagline and notice line.
2. **Search box** — slim input with a search icon; filters by item name/description live; shows "No dishes found". Scrolls away with the header. Below it, a small icon key (Spicy / Vegetarian / Chef's special).
3. **Sticky category tabs** (horizontal scroll, plain uppercase text, active tab = white text + 2px red underline). Tapping scrolls to the section; the active tab highlights while scrolling (IntersectionObserver) and scrolls into view.
4. **Sections per category** as a printed-menu style list (no cards):
   - Name on the left, a fine dotted leader, and price (`Rs. 1,200`) right-aligned on the same line. The leader shrinks to nothing for long names; the price never wraps.
   - If `price_large`: a "Regular / Large" block on the right, spanning beside the name and description (the description sits directly under the name).
   - Description below (max 2 lines). Thin divider between rows.
   - Category headings, dividers (line + small flame + line), the tagline and the footer's "Prices may change" note are framed by hairlines echoing the lines beside "Restaurant" in the logo. The tagline only gets lines when it fits on one line with them.
   - Small inline SVG icons after the name: flame (spicy), leaf (veg), star (chef's special), each with a visually hidden text label.
   - Photo (if any) as a 72px rounded thumbnail on the left, lazy-loaded with fixed size. If any dish in a category has a photo, rows without one keep the same indent.
   - Sold-out items: hidden, or faded with "Sold out today" if `show_sold_out` is TRUE.
5. **Footer:** opening hours, address, "Call us" button (outlined; red while pressed), "Directions" link (Google Maps), small "Prices may change" note, small developer credit.
6. **Back-to-top** button after scrolling (small dark circle, white arrow).

### Behaviour
- Show a **skeleton loader** while fetching.
- Save the last successful menu to `localStorage`; render cached data instantly on next visit, then refresh in the background.
- On failure with no cache → friendly error + call button.
- Must work without photos.

### Visual style
- Dark, minimal, premium — matches the black/white/red logo. **Dark theme only** (no light/dark switching).
- Colours (CSS variables in `css/style.css`): background `#0b0b0b`, surface `#151515` (only where needed), text `#f5f5f5`, secondary text `#a3a3a3`, thin dividers in low-opacity white.
- **Red is the only brand accent**: `#e7190c` (sampled from the logo), used only for the active tab underline, spicy flame icon, focus ring and pressed Call button. Never for text (it is 4.26:1 on the background, below WCAG AA's 4.5:1 for text).
- **Icon colours carry meaning** (dish rows and the icon key use the same colours): spicy flame = logo red `#e7190c`; vegetarian leaf = soft green `#5dbb63` (8.2:1); chef's special star = soft off-white `#e0e0e0`. All exceed the 3:1 needed for icons. Only icons are coloured, never dish names, prices or rows. Meaning never relies on colour alone: each icon has a distinct shape and a hidden text label.
- **Prices are deliberately understated** so attention goes to the food, not the cost: soft white `#e0e0e0`, weight 500, slightly smaller than the dish name, tabular numbers, right-aligned. The "Rs." prefix is smaller and grey; "Regular/Large" labels are grey.
- No gold, gradients, glows, heavy shadows, card grids or emojis.
- Font: **Montserrat** from Google Fonts (weights 500, 600, 800 only, `display=swap`) with a system-font fallback. Category headings uppercase, 800, letter-spaced. No script fonts outside the logo image.
- All text meets WCAG AA contrast; focus states visible; `prefers-reduced-motion` turns off smooth scrolling and animations.

## 6. Admin page — `admin.html`

Designed for **non-technical owners using only a phone**.

### Screens
1. **Login screen:** email and password fields (with `autocomplete="username"` / `"current-password"` so the phone can save them), a "Show password" option and a **Log in** button. Firebase Authentication `signInWithEmailAndPassword`. Clear, friendly messages for a wrong email/password and for "too many attempts, try again later" (Firebase's own protection). The owner **stays signed in** (local persistence) until they log out. No sign-up option.
2. **Menu manager:**
   - Top bar: "Hot Wok – Menu Manager", **Logout**, link "View customer menu".
   - Category filter dropdown + search.
   - Each item row: name, price, **large availability toggle switch**, ✏️ Edit button.
   - **Toggle** saves immediately and shows a toast "Chicken Kottu hidden from menu" / "…is back on the menu".
   - Floating **"+ Add dish"** button.
3. **Edit / Add form** (full-screen sheet on mobile): name, category (dropdown), price, large price (optional), description, spicy / veg / chef's special checkboxes. **No photo field.** The admin page never handles images. Buttons: **Save**, **Cancel**, and on edit **Delete** (red, with "Are you sure you want to delete Chicken Kottu?" confirmation).
4. Optional ↑ ↓ buttons to reorder items.

### UX rules
- Big buttons (≥ 48px), large text, plain English labels (no technical words like "record" or "API").
- Disable buttons and show a spinner while saving; never allow double-submit.
- Every action ends with a clear success or error toast.
- If the owner is signed out (or a save fails with `permission-denied` because the account isn't allowed), return to the login screen with a plain message.
- Each save is one Firestore transaction (see 4.3). Show "Saved" only after Firestore confirms.
- `manifest.json` + icons so the owner can **Add to Home screen** with the name "Hot Wok Menu" and `start_url` = `admin.html`.
- Add `<meta name="robots" content="noindex">` to admin.html.

## 7. QR code — `tools/generate-qr.js`

- Node script using the open-source `qrcode` npm package (dev dependency only).
- Encodes the final customer menu URL **https://hotwokrestaurant.github.io/** (static QR — never expires).
- ⚠️ Once printed, the QR can't change: never rename the `hotwokrestaurant` organization or the `hotwokrestaurant.github.io` repo.
- Outputs `qr/menu-qr.png` (high resolution, ≥ 1000 px) and `qr/menu-qr.svg`.
- Error correction level **M** (or **H** if a logo is placed in the centre later).
- Also generate `qr/table-card.html`: a printable A6 table card with the restaurant name, "Scan for our menu 📱", the QR code, and the short URL `hotwokrestaurant.github.io` underneath.

## 9. Acceptance checklist

- [ ] Customer menu loads in under ~3 seconds on Slow 4G.
- [ ] No horizontal scrolling at 360px width.
- [ ] Wrong password rejected; the owner stays signed in after closing and reopening the phone browser.
- [ ] Signed-out writes and writes from a non-allow-listed account are rejected (security rules).
- [ ] No passwords, Google account details or keys in the repository (only the public Firebase web config).
- [ ] Firebase project is on the Spark plan; no billing account attached.
- [ ] Public sign-up disabled in Authentication settings (if available); `admins` contains only the owner's UID and can't be written by any app.
- [ ] Two phones editing different dishes at the same time both keep their changes.
- [ ] Developer files (`/firebase/…`, `/docs/…`, `/CLAUDE.md`) are not served on the live site (404).
- [ ] A menu backup has been downloaded and a restore has been tested.
- [ ] Price change in admin → visible on customer menu after refresh.
- [ ] Sold-out toggle hides the item for customers.

- [ ] Owner Guide written in simple language.
