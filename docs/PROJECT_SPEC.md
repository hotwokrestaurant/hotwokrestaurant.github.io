# Hot Wok Restaurant — QR Digital Menu: Project Specification

Version 2.0 (Firebase backend) · Place this file at `docs/PROJECT_SPEC.md`.

---

## 1. Goals

| # | Goal |
|---|---|
| G1 | Customers scan a QR code and see a clear, fast, mobile-friendly menu. |
| G2 | The owner can change prices, mark items sold out, add and delete items **from their phone only**. |
| G3 | Zero running cost, no payment features, no paid tools. |
| G4 | Simple enough for a beginner developer to understand and maintain. |

### Out of scope (v1)
Online ordering, payments, table numbers, customer accounts, reviews, delivery, dish photo upload from the admin page (not planned: Cloud Storage needs billing; photos are added to `images/` by the developer), multiple languages (planned for v2).

## 2. Architecture

```
Customer phone ──scan QR──► index.html  (GitHub Pages)
                                │ 1 read: REST GET menu/published   [plain fetch(), no SDK]
                                ▼
                    Cloud Firestore  (Spark free plan, asia-south1)
                       ▲    protected by firebase/firestore.rules
                       │ sign in (Firebase Auth) + save menu/published   [Firestore + Auth SDK]
Owner phone ──home icon──► admin.html  (GitHub Pages)
```

- Firestore = database. Firebase Authentication = owner login. Security rules = all access control and validation. GitHub Pages = static hosting. **No server code.**
- Customer menu: **https://hotwokrestaurant.github.io/** · Admin: **https://hotwokrestaurant.github.io/admin.html**
- Repo: `hotwokrestaurant/hotwokrestaurant.github.io` (GitHub organization Pages site; the repo name must stay exactly this for the root URL to work).
- The customer page only reads (one document per visit). The admin page reads and writes.
- **Spark plan only.** Nothing that needs billing: no Blaze upgrade, no Cloud Storage, no Cloud Functions, no paid extensions.
- Setup instructions: `firebase/README.md`.

## 3. Data model (Cloud Firestore)

### 3.1 The menu document: `menu/published`

The **whole published menu is one document**, so each customer visit costs a single read. Its shape is the same as `firebase/menu-seed.json`, plus `updatedAt`.

| Field | Type | Notes |
|---|---|---|
| `settings` | map | See 3.4 |
| `categories` | map of menu sections, keyed by section id | See 3.3. 1–25 sections |
| `items` | array of maps | See 3.2. Up to 200 entries |
| `updatedAt` | timestamp | Set with `serverTimestamp()` on every save (the rules require the server's clock) |

The document is about 5 KB with 18 dishes. Firestore's limit is 1 MiB, so size is never a concern.

### 3.2 Items (dishes): entries of `items`

| Field | Type | Rules / example |
|---|---|---|
| `id` | string | `itm_` + 4–20 lower-case letters/digits, e.g. `itm_ko0001`. Generated by the admin page, never typed by hand. |
| `category_id` | string | The **id** of the dish's section, which must exist in `categories` (3.3), e.g. `cat_kottu`. Renaming a section never touches dishes. |
| `name` | string | Required, 1–60 chars. e.g. `Chicken Kottu` |
| `description` | string | Optional, ≤ 150 chars (`''` = none) |
| `price` | integer | Required, whole rupees, 1–100,000. e.g. `1200` |
| `price_large` | integer or `null` | Optional. `null` = one size only |
| `spicy` | boolean | |
| `veg` | boolean | |
| `available` | boolean | `false` = sold out today (hidden, or faded if `show_sold_out`) |
| `featured` | boolean | Shows the "Chef's special" icon |
| `image` | string | Optional. Simple file name in the repo's `images/` folder, e.g. `chicken-kottu.webp`; `''` = no photo. **Set by the developer only; the admin page never handles images.** |
| `sort_order` | integer | 0–10,000. Lower shows first within its category |

### 3.3 Menu sections (categories): the `categories` map

Each section has a **permanent id** (the map key), managed by the owner in the admin page (Menu sections):

```json
"categories": {
  "cat_friedrice": { "name": "Fried Rice", "sort_order": 1, "visible": true },
  "cat_kottu":     { "name": "Kottu",      "sort_order": 2, "visible": true }
}
```

| Part | Type | Rules |
|---|---|---|
| key (id) | string | `cat_` + 4–20 lower-case letters/digits. Never changes. Seed sections use readable ids (`cat_kottu`); new ones get random ids (`cat_k3x9q2mf`). |
| `name` | string | 1–30 characters. Unique, ignoring capitals (checked by the admin page; the rules can't check this cheaply). |
| `sort_order` | integer | 0–1,000. The order of the tabs on the customer menu |
| `visible` | boolean | `false` = the section and all its dishes are hidden from customers |

**Why a map and not a list:** the rules must check that every new or changed dish's `category_id` exists. With a map that's one cheap lookup (`category_id in categories`). With a list, it means walking the list, which costs about 25 rule steps per section and broke the 1,000-step limit with 15+ sections (measured).

Deleting a section also deletes all its dishes, in **one** save, so no dish is ever left pointing to a missing section (see 4.3). The rules can't check this cheaply; the admin page guarantees it by removing both in the same transaction. If a dish's section were ever missing anyway, the customer page wouldn't show the dish, and the admin page would list it under "Not in a section".

## 4. Firebase access

### 4.1 How each page talks to Firebase (no build step)
- **Customer page: no Firebase SDK.** It reads the public document with one plain `fetch()` to the Firestore REST API:
  `GET https://firestore.googleapis.com/v1/projects/<projectId>/databases/(default)/documents/menu/published?key=<apiKey>`
  - The response is about 1.9 KB compressed, instead of about 61 KB of SDK code.
  - It's a simple GET, so the browser skips its extra CORS check request.
  - Firestore allows the `hotwokrestaurant.github.io` origin.
  - The security rules apply as for any signed-out visitor.
  - A small converter in `js/api.js` turns Firestore's typed values back into plain values: `stringValue`, `integerValue` (sent as text, converted to a number), `doubleValue`, `booleanValue`, `nullValue`, `timestampValue` (converted to milliseconds), `arrayValue`, `mapValue` (keys sorted).
- **Admin page:** Firebase **modular SDK** as ES module imports from Google's official CDN, **pinned to one version** in every URL: `https://www.gstatic.com/firebasejs/12.19.0/<file>.js` (`firebase-app.js` + `firebase-firestore.js` + `firebase-auth.js`). Upgrade by changing every URL together and re-testing.
- Config (`FIREBASE_CONFIG`) and the document path (`MENU_COLLECTION` / `MENU_DOC_ID`) live in `js/config.js`. The web config is not a secret.

### 4.2 Customer reads (Phase 3, `js/api.js` + `js/menu.js`)
1. On load, render the **saved** menu from `localStorage` (key `hotwok.menu.v1`: `{ menu, updatedAt }`, `updatedAt` in milliseconds) immediately, if one exists. Otherwise the skeleton stays.
2. Fetch the latest menu with **one REST `fetch()`** (see 4.1; = 1 read per visit). Nothing has to download first, so it never delays the saved menu or the skeleton. `index.html` preconnects to Firestore and `modulepreload`s the page's own helper modules.
3. A **timeout** covers the whole download and cancels it (`AbortController`): 20 s on a first visit, 10 s when a saved menu is already shown (`js/config.js`).
4. On success: redraw **only if the menu changed** (`updatedAt` differs, or the contents differ, which catches hand edits in the Firebase console that don't touch `updatedAt`), and save to `localStorage` (try/catch). A redraw keeps any search text and skips the fade-in.
5. On failure (offline, timeout, missing/invalid data): with a saved menu, show the small note "Showing saved menu · updated 29 Oct"; with none, show a friendly message with **Try again** and **Call us** (number from `FALLBACK_PHONE` in `js/config.js`). When the phone comes back online, the menu quietly retries.
6. Filtering stays in the browser: only `visible` categories; only `available` items unless `show_sold_out`.
7. **No sample data in the live site.** All text, including the notice and the footer details, comes from `settings` in Firestore (the seed no longer has a "Sample menu" notice). `js/sample-data.js` was removed in Phase 3; `firebase/menu-seed.json` is the reference data.
8. A fully offline **first** page load can't work without a service worker (not in v1). "Offline" here means the page itself loaded (from the network or the browser's cache) but Firestore couldn't be reached.

Measured (headless Chrome against the live project, 412px wide). The REST fetch replaced Firestore Lite because it was clearly faster on first visits and behaved the same in every failure test:

| Scenario | Firestore Lite SDK | **REST fetch (current)** |
|---|---|---|
| First visit, normal connection | 2.5 s | **1.0–1.2 s** |
| Repeat visit | 0.1 s (saved copy) | **0.1 s** (saved copy) |
| Slow 3G, first visit (3 runs) | 12.0–12.4 s | **7.7–8.2 s** |
| Slow 3G, repeat visit, no browser cache (3 runs) | 5.5–5.6 s | **5.5–5.6 s** (saved copy; page files take the time) |
| Firestore unreachable, saved copy | 0.1 s + note | **0.1 s + note** |
| Firestore unreachable, nothing saved | error at 0.9 s | **error at 0.5–0.8 s** |
| Firestore not answering, saved copy | note at 10 s | **note at 10 s** |
| Firestore not answering, nothing saved | error at 21 s | **error at 21 s** |
| Saved copy out of date (same `updatedAt`) | corrected | **corrected** |

### 4.3 Owner writes (Phase 4): never overwrite the menu
The admin page **never** writes the whole document with `setDoc`. Every change (toggle sold out, edit, add, delete, reorder, settings) is a **transaction that updates only the field it changes**:

```js
await runTransaction(db, async (tx) => {
  const snap = await tx.get(menuRef);                    // 1. read the LATEST menu
  const items = snap.data().items.map((it) =>
    it.id === dishId ? { ...it, available: false } : it); // 2. change one dish in it
  tx.update(menuRef, { items, updatedAt: serverTimestamp() }); // 3. write only items + updatedAt
});
```

- **Why a transaction:** if another phone saves between steps 1 and 3, Firestore notices that the document changed and **re-runs the function with the fresh menu**. Two phones editing different dishes at the same moment both keep their change; neither can wipe the other's.
- **Why `tx.update` of one field:** a dish change writes only `items` (+ `updatedAt`); a settings change writes only `settings`; a category change writes only `categories`. Unrelated parts of the document are never rewritten.
- **Why not `items.<id>` field paths:** that only works if `items` is a map. The data model keeps `items` as an array (same shape as `firebase/menu-seed.json`), and the transaction gives the same protection.
- **Tested** against the current rules in the Firestore emulator: two simultaneous transactions on different dishes keep both edits; a settings-only transaction leaves dishes untouched; an invalid dish inside a transaction is still rejected. No rule changes are needed.
- If the same dish is edited on two phones at once, the later save wins for that dish (expected).
- Each save sets `updatedAt: serverTimestamp()`.
- **A save may add or change at most 3 dishes or 10 sections**, and **a save that changes the sections can't also change dishes** (rules limits, see 4.4). Normal actions touch 1 dish or section (reorder: 2). Deleting dishes is unlimited. Settings may change together with dishes.
- New dish: `id` = `itm_` + random lower-case letters/digits, `category_id` = the chosen section, `available: true`, `sort_order` = last in its section.
- **Sections** (`saveSections`): same transaction pattern, writing only `categories`:
  - add: new id `cat_` + random letters/digits, last in order, shown;
  - rename: only `name` changes;
  - reorder: swap the `sort_order` of two neighbours;
  - show/hide: `visible`;
  - delete (`saveSectionsAndItems`): **one transaction removes the section and all its dishes** (all or nothing; a lost connection changes nothing). The rules allow it because removing dishes needs no checks; only new or changed dishes do. Inside the transaction the dishes in that section must be exactly the ones the owner saw listed; if another phone added or removed one meanwhile, it stops with "This section was just changed on another phone…". The last section can't be deleted.
  - **Undo** (10 seconds after a delete): re-adding dishes must be fully checked (3 per save), so it runs in safe, repeatable steps:
    1. the section comes back **hidden**, with its original id, name and order;
    2. its dishes come back 3 per save, with original ids, details and order (only the missing ones);
    3. the section is switched back to its original visibility.

    Customers never see a half-restored section, and dishes always point to an existing section. A progress message shows "Bringing back "Kottu"… 6 of 20 dishes". What's needed to finish is kept on the phone (`localStorage`, key `hotwok.admin.pendingUndo`). If the connection drops, the message says "…stopped: 6 of 20 dishes are back… tap Continue". After a reload, the admin page offers to finish ("…was only partly brought back… Continue").
  - Names are checked for duplicates (ignoring capitals) on screen and again inside the transaction.
- Frontend validation mirrors the rules (same limits) so the owner gets friendly messages, but the **rules are the real check**.

### 4.4 Security rules (`firebase/firestore.rules`)
- **Read:** anyone can `get` `menu/published`. Listing collections and reading anything else are denied.
- **Write:** only signed-in users whose UID has a document in `admins`, and only if the new document is valid:
  - Exact top-level fields, and `updatedAt == request.time`.
  - Settings types and sizes.
  - Sections: 1–25 in total; every **new or changed** section has exactly `name` (1–30 characters), `sort_order` (integer 0–1,000) and `visible` (boolean); every new id looks like `cat_…`; at most 10 sections change per save.
  - Every **new or changed** dish fully validated: types, name ≤ 60, description ≤ 150, prices positive integers, `category_id` must exist in `categories` (one map lookup), safe image name, no unknown fields.
- **Why only changed data:** rules have no loops, so they can't check every dish or section in a list. They compute `newItems.removeAll(oldItems)` (and the same for section values and ids), cap the count, and validate each. Settings are likewise only checked when they change. Every value is therefore validated when it's written.
- **Why the limits are 3 dishes, 10 sections, and "sections alone":** Firestore stops evaluating a rule after 1,000 steps, and it counts every small step. Measured in the emulator with **25 sections and 150 dishes**, every allowed kind of save fits: add, rename, reorder, hide, show and delete a section; 10 sections at once; add, edit or move a dish (in the last section); 3 dishes; settings + 3 dishes. Text is checked with one pattern each (e.g. `name.matches('.{1,30}')`) to keep the cost down.
- **Not checked by the rules (too expensive without loops):** unique section names, and that no dish is left pointing to a deleted section. The admin page ensures both inside its save transaction (a section is always deleted together with its dishes).
- **Deleting a section with its dishes** is one allowed save (removals aren't checked); **Undo** re-adds dishes 3 per save, each fully checked. Measured with 25 sections and 150 dishes: deleting a section with 6 or 20 dishes, and every Undo step, fits under the 1,000-step limit.
- **`admins` is write-locked for every app** (`allow list, write: if false`). A signed-in account can only `get` its own entry (`request.auth.uid == uid`), which the admin page uses after login. Only the Firebase console can change it, so an account created through the Auth API can't add itself. Public sign-up is also turned off in Authentication → Settings → User actions, where the console offers it.
- No deletes of the menu document. Everything not matched is denied.
- **Settings checks:** phone and WhatsApp only digits, `+` and spaces (≤ 30); email empty or a simple `name@domain.tld`; map and Facebook links empty or `https://` with no spaces (≤ 300); the optional keys are checked only when present. Each is one pattern, so "settings + 3 dishes" still fits under 1,000 steps.
- Tested in the Firestore emulator (110 checks, all passing, including the `admins` lockdown, own-entry reads, simultaneous transactions, sections, deleting sections with 0/1/5/20 dishes and undoing them, the one-time upgrade, and the contact fields) plus the 25-section/150-dish step-limit test (23 kinds of save) before handover; manual tests are in `firebase/README.md`.

### 4.5 Owner authentication
- Email/password. The owner's account is created by hand in the console. **No sign-up flow** in the app (and "Enable create (sign-up)" is turned off in the console where available).
- **Persistence:** `browserLocalPersistence`, so the owner stays signed in on their phone until they press **Log out**.
  - iPhone Safari may clear site storage after ~7 days without a visit. Adding the admin page to the Home Screen (Phase 5) avoids this. Otherwise the owner just signs in again.
- Authorized domains: `hotwokrestaurant.github.io` and `localhost`.

### 4.6 App Check
Not enabled in v1. reCAPTCHA would slow the customer page on 3G and can block real customers, and the rules already stop any unauthorized changes. Reconsider only if usage shows abuse. Full reasoning: `firebase/README.md`.

### 4.7 Backups (no automatic backups on Spark)
- **Phase 4:** a **"Download backup"** button in the admin page saves `menu/published` as a `.json` file in the same shape as `firebase/menu-seed.json` (`settings`, `categories`, `items`; no `updatedAt`). File name like `hot-wok-menu-backup-2026-11-03.json`. Uses the read the admin page has already done; no extra cost.
- **Restore:** `firebase/setup.html` step 5, **"Restore from a backup file"** (built in Phase 4). It reuses the seed loader: settings + sections first (10 per save), then 3 dishes per save, so the rules check everything. Backups in the old format (made before the sections upgrade) are converted automatically.
- **Optional later:** a scheduled GitHub Action reads the public document once a day and commits it to a separate `backups` branch. That's free, needs no credentials, and doesn't trigger a Pages deploy.
- Owner guidance: download a backup after big changes and monthly; keep it in Google Drive or email.

### 4.8 What is published
GitHub Pages publishes the repo root, except what `_config.yml` excludes: `firebase/` (rules, seed, setup page, guide), `docs/`, `tools/`, `CLAUDE.md`, `README.md`. Developer tools therefore stay in the repo but are never served. Don't add a `.nojekyll` file; the exclusions rely on Pages' default Jekyll build. Check after each deploy that `/firebase/setup.html` returns 404.

### 4.9 One-time sections upgrade (old format → section ids)
Menus created before the "Menu sections" feature store sections as a list without ids, and dishes point to the section **name** (`category: 'Kottu'`). `firebase/setup.html` step 6 upgrades them:
1. **Download a backup first.** The upgrade button stays locked until the backup is downloaded.
2. Transaction A: sections list → map with permanent ids. The ids are made from the names (`Fried Rice` → `cat_friedrice`), the same as `menu-seed.json`. Dishes are unchanged.
3. Transactions B…: dishes 3 per save, `category: 'Kottu'` → `category_id: 'cat_kottu'`.
4. Safe to run again (it continues, or says "already up to date"), and safe while the owner edits (every step is a transaction on the latest menu).

During the switch-over:
- **The customer page reads both formats.** Dishes are matched by `category_id` when present, otherwise by section name, so the menu never breaks.
- **The admin page shows "The menu needs a one-time update"** until the upgrade is done.
- **The new rules accept the upgrade steps:** unchanged old-format dishes aren't re-checked, and every converted dish must point to an existing section.

**Real restaurant details:** `firebase/setup.html` step 7 copies `phone`, `whatsapp`, `email`, `address`, `opening_hours`, `map_url` and `facebook_url` from `menu-seed.json` into the live `settings` in one transaction (`tx.update` of `settings` only). It also clears the old "Sample menu – prices are placeholders" notice. Dishes and sections are untouched. The owner can also type them in **Restaurant details**. The fallback phone for the error screen is `FALLBACK_PHONE` in `js/config.js` (+94 70 270 1009).

Tested on the emulator: the customer menu was identical before and after, the result equals `menu-seed.json`, and running it twice was harmless.

### 4.10 Free limits (Spark)
50,000 reads, 20,000 writes and 20,000 deletes per day; 1 GiB stored. Each customer visit = 1 read. Hitting a limit pauses Firestore until the daily reset (no charges); customers then see the cached menu.

## 5. Customer menu — `index.html`

### Layout (top to bottom)
1. **Header:** logo image (`images/logo.webp`, the wordmark cropped from the original `images/logo.jpg`, shown 232px wide) as the page title, optional tagline and notice line.
2. **Search box** — slim input with a search icon; filters by item name/description live; shows "No dishes found". Scrolls away with the header. Below it, a small icon key (Spicy / Vegetarian / Chef's special).
3. **Sticky category tabs** (horizontal scroll, plain uppercase text, active tab = white text + 2px red underline). Tapping scrolls to the section; the active tab highlights while scrolling (IntersectionObserver) and scrolls into view.
4. **Sections per category** as a printed-menu style list (no cards):
   - Name on the left, a fine dotted leader, and price (`Rs. 1,200`) right-aligned on the same line. The leader shrinks to nothing for long names; the price never wraps.
   - If `price_large`: a "Regular / Large" block on the right, spanning beside the name and description (the description sits directly under the name).
   - Description below (max 2 lines). Thin divider between rows.
   - Category headings, dividers (line + small flame + line), the tagline and the footer's "Prices may change" note are framed by hairlines echoing the lines beside "Restaurant" in the logo. The tagline only gets lines when it fits on one line with them.
   - Small inline SVG icons after the name: flame (spicy), leaf (veg), star (chef's special), each with a visually hidden text label.
   - Photo (if any) as a 72px rounded thumbnail on the left, lazy-loaded with fixed size. If any dish in a category has a photo, rows without one keep the same indent.
   - Sold-out items: hidden, or faded with "Sold out today" if `show_sold_out` is TRUE.
5. **Footer**, centred, from top to bottom:
   - Divider: hairline + small flame + hairline.
   - **OPENING HOURS** (framed heading like the section titles), then the hours (line breaks kept).
   - **FIND US**: the address and a **Directions** link (Google Maps).
   - **CONTACT**: the phone number as text, then **Call / WhatsApp / Email / Facebook** buttons with small line icons (inline SVG). They are outlined white and turn red while pressed, at least 48px tall, 2 × 2 on a 360px phone, and one per line on very narrow screens or with large text. A button with an empty value is hidden; the whole block hides if all are empty.
   - Closing mark: "Prices may change without notice." No developer credit.
6. **Back-to-top** button after scrolling (small dark circle, white arrow).

### Behaviour
- Show a **skeleton loader** while fetching. **Nothing may jump when the menu arrives** (target: layout shift / CLS under 0.1):
  - The skeleton looks like the real first section (centred heading bar, dish-shaped rows with the same padding and dividers) and is at least one screen tall.
  - The empty tagline keeps one line of space, and the tab bar keeps its 48 px height while empty, so the search box and tabs don't move.
  - The footer is hidden while `#menu` has `aria-busy="true"` (CSS only). It appears below the menu, or below the error message.
  - Measured with live data (headless Chrome, normal and Slow 3G): first and repeat visits at 360px, 412px and 1280px give CLS 0.000–0.001 (was 0.53–0.83). Expected small shifts that can't be reserved in advance: an owner notice appearing on a first visit (0.03), and a tagline that wraps to two lines at 200% text size (0.04).
- Save the last successful menu to `localStorage`; render cached data instantly on next visit, then refresh in the background.
- On failure with no cache → friendly error + call button.
- Must work without photos.

### Visual style
- Dark, minimal, premium — matches the black/white/red logo. **Dark theme only** (no light/dark switching).
- Colours (CSS variables in `css/style.css`): background `#0b0b0b`, surface `#151515` (only where needed), text `#f5f5f5`, secondary text `#a3a3a3`, thin dividers in low-opacity white.
- **Red is the only brand accent**: `#e7190c` (sampled from the logo), used only for the active tab underline, spicy flame icon, focus ring and pressed Call button. Never for text (it is 4.26:1 on the background, below WCAG AA's 4.5:1 for text).
- **Icon colours carry meaning** (dish rows and the icon key use the same colours): spicy flame = logo red `#e7190c`; vegetarian leaf = soft green `#5dbb63` (8.2:1); chef's special star = soft off-white `#e0e0e0`. All exceed the 3:1 needed for icons. Only icons are coloured, never dish names, prices or rows. Meaning never relies on colour alone: each icon has a distinct shape and a hidden text label.
- **Prices are deliberately understated** so attention goes to the food, not the cost: soft white `#e0e0e0`, weight 500, slightly smaller than the dish name, tabular numbers, right-aligned. The "Rs." prefix is smaller and grey; "Regular/Large" labels are grey.
- No gold, gradients, glows, heavy shadows, card grids or emojis.
- Font: **Montserrat** from Google Fonts (weights 500, 600, 800 only, `display=swap`). Category headings uppercase, 800, letter-spaced. No script fonts outside the logo image.
  - **The page never waits for Google Fonts** (`index.html` and `admin.html`): preconnect, then the stylesheet loads with `media="print" onload="this.media='all'"`, plus a `<noscript>` copy. Text shows at once in a local font and swaps to Montserrat when it arrives.
  - **Matched fallback** (`css/style.css`): `Montserrat Fallback Roboto` (Android) and `Montserrat Fallback Arial` (iPhone, computers) are local fonts with `size-adjust` per weight (Montserrat is 7–18% wider) and ascent/descent overrides. Measured at 360px: the swap moves nothing (0 dishes re-wrap, 0 px); without it, 3 dishes re-wrap and content jumps up to 69 px. Old browsers ignore `size-adjust` and show the plain local font.
  - Measured on the customer page (headless Chrome, live data, first visit): if Google Fonts takes 6 s, text appears at **0.1 s instead of 6.4 s**, dishes at **0.5 s instead of 6.7 s**. If Google Fonts doesn't answer, the old page stayed blank, and the new one shows the menu in about 0.5 s. On uniform Slow 3G and on repeat visits, timings are unchanged (~5.6 s text first visit, ~0.1 s repeat).
- All text meets WCAG AA contrast; focus states visible; `prefers-reduced-motion` turns off smooth scrolling and animations.

## 6. Admin page — `admin.html`

Designed for **non-technical owners using only a phone**.

Files: `admin.html`, `css/admin.css`, `js/admin.js` (screens and UI), `js/admin-firebase.js` (every Firebase call), `js/admin-strings.js` (all UI text; English now, Sinhala later by adding a `si` block).

### Screens (as built in Phase 4)
1. **Log in:** logo, email + password (52px fields, phone can save them), "Show password", **Log in**, "Forgot password?" (sends a reset email; never reveals whether the email exists). Plain messages for wrong email/password, too many tries, no internet, account switched off. The owner **stays logged in** until they press **Log out**.
2. **After log in:** the page checks the account's own `admins` entry. If it's not there: "This account can't edit the menu" + **Log out**. (The rules block such an account anyway.)
3. **Menu manager:**
   - Top: "Menu Manager", "Logged in as …", **Log out**.
   - "Find a dish" search; **+ Add a dish**; **Change order** (shows ↑ ↓ arrows; **Done** to finish).
   - Dishes grouped by category (hidden categories marked "not shown to customers").
   - Each row: name; price ("Rs. 950 · Large Rs. 1,300"); an **"Available today" ON/OFF switch** that saves at once ("Chicken Kottu is hidden from the menu" / "…is back on the menu"); **Edit**.
   - Bottom ("More"): **Restaurant details**, **Download backup**, **View customer menu**.
   - Other phones' changes appear live (the page listens for menu changes).
4. **Dish form** (full-screen; the phone's Back button closes it): name (≤ 60), category, price, large price (optional), description (≤ 150, live "letters left" counter), Spicy / Vegetarian / Chef's special. Prices accept "1,250". **Save** / **Cancel** stay visible at the bottom. On edit, red **Delete this dish** with a confirmation naming the dish. **No photo field.**
5. **Restaurant details form:** notice, opening hours, phone, WhatsApp, email, address, Google Maps link, Facebook link. It checks the same rules as `firestore.rules`, with plain messages: phone/WhatsApp only numbers, spaces and +; email like name@gmail.com; links start with `https://` and have no spaces. Other settings (name, tagline, show sold out) are kept unchanged.
6. **Menu sections** (main screen → More → Menu sections): sections in menu order. Each row shows the name and dish count ("5 dishes", "Hidden"), a big **"Shown on menu" ON/OFF switch**, ↑ ↓ arrows (the tab order on the customer menu), **Rename** and **Delete** (red outline).
   - **+ Add a section** / **Rename** open a small form: name up to 30 letters; duplicates are refused, ignoring capitals ("There is already a section called "Kottu"").
   - **Delete** an empty section: simple confirmation naming it. A section **with dishes** opens a full-screen dialog:
     - **Title:** "Delete "Kottu" and its 20 dishes?"
     - **Dish names:** the first 5, plus "…and 15 more".
     - **Buttons:** a red **Delete section and 20 dishes**, **Hide section instead** (switches it OFF), and **Cancel**.

     After deleting, a message "Kottu" and 20 dishes deleted with a big **Undo** button stays for 10 seconds (see 4.3). The last section can't be deleted.
   - The dish form's section dropdown lists every section, hidden ones as "Name (hidden)".
   - The phone's Back button closes one layer at a time (name form → sections list → main screen).
7. **"The menu needs a one-time update"** is shown instead of the manager if the saved menu is still in the old format (see 4.9).

### UX rules
- Text 18px base; every button and field at least 48px tall; plain words (no "document", "field", "UID", "database").
- While saving: the button shows a spinner + "Saving…" and is disabled. Every action ends with a short message at the top of the screen (at most 2 at once). Errors are in plain words.
- Offline: a red banner "You are offline…", and saves are refused with a clear message (nothing is half-saved).
- Each save is one Firestore transaction changing only `items` or `settings` (see 4.3). "Saved" is shown only after Firestore confirms.
- Validation in the form mirrors the rules, but the **rules are the real check**.
- `manifest.json` + icons so the owner can **Add to Home screen** (Phase 5).
- `<meta name="robots" content="noindex, nofollow">` on admin.html.

## 7. QR code — `tools/generate-qr.js`

- Node script using the open-source `qrcode` npm package (dev dependency only).
- Encodes the final customer menu URL **https://hotwokrestaurant.github.io/** (static QR — never expires).
- ⚠️ Once printed, the QR can't change: never rename the `hotwokrestaurant` organization or the `hotwokrestaurant.github.io` repo.
- Outputs `qr/menu-qr.png` (high resolution, ≥ 1000 px) and `qr/menu-qr.svg`.
- Error correction level **M** (or **H** if a logo is placed in the centre later).
- Also generate `qr/table-card.html`: a printable A6 table card with the restaurant name, "Scan for our menu 📱", the QR code, and the short URL `hotwokrestaurant.github.io` underneath.
